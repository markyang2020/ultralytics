# 电动自行车部件外观特征比对 Demo 设计

## 1. 目标

实现一个可直接运行的命令行 Demo，验证以下完整链路：

1. 使用已训练的 YOLO 部件检测模型分别检测 3C 合格证官方图和现场实拍图。
2. 对双方共同检测到的同类别部件进行裁剪。
3. 使用 DINOv2 ViT-B/14 提取部件的 768 维外观特征。
4. 对特征进行 L2 归一化并计算余弦相似度。
5. 输出每个部件的相似度分档、原始数据和可视化证据。

本 Demo 用于验证《电动自行车备案图与实拍图一致性比对技术方案》中 Level 2 部件外观特征比对方法，不负责验证 Level 3 结构关系，也不把单次实验分数直接作为生产判定阈值。

- 备案图：订单目录下的 `reference_3c.jpg`
- 实拍图：订单目录下的 `actual_left_front_45.jpg`

权重包含 12 个类别：`ebike_full`、`front_headlight`、`front_basket`、`mirror`、`pedal`、`saddle`、`reflector`、`rear_box`、`seat`、`rack`、`backrest`、`center_box`。

## 3. 方案选择

采用“可解释的 PDF 原始方法”：核心算法保持 YOLO 检测框裁剪、DINOv2 CLS token 和余弦相似度，不在第一版加入多裁剪、特征融合、图像配准或额外模型。

第一版保持单一路径，原因如下：

- 与现有技术方案一致，便于确认实现和文档描述是否相符。
- 每个相似度都能追溯到检测框和部件裁剪图。
- 为后续视角对齐、多视图融合和阈值标定提供可重复的基线。
- 避免在没有正负配对标注集的情况下引入无法量化收益的增强逻辑。

## 4. 命令行接口

Demo 支持直接指定订单目录，也支持分别指定两张图片：

```bash
python ebike_part_feature_compare.py \
    --order-dir /path/to/order \
    --detector /path/to/yolo.pt \
    --device cpu
```

等价的显式图片模式：

```bash
python ebike_part_feature_compare.py \
    --reference /path/to/reference_3c.jpg \
    --actual /path/to/actual_left_front_45.jpg \
    --detector /path/to/yolo.pt
```

主要参数：

- `--order-dir`：从目录中读取固定文件名的备案图和实拍图。
- `--reference`、`--actual`：显式指定图片，和 `--order-dir` 二选一。
- `--detector`：YOLO 权重路径。
- `--det-conf`：检测置信度阈值，默认 `0.60`，与技术方案的 Level 2 参与条件一致；可显式调整为 `0.12` 观察低置信候选框。
- `--similar-threshold`：一致阈值，默认 `0.80`。
- `--review-threshold`：疑似阈值，默认 `0.60`。
- `--device`：推理设备，默认自动选择，也可指定 `cpu`、`mps` 或 CUDA 设备编号。
- `--output-dir`：输出目录；未指定时写入 `validate/part_feature_compare/runs/<订单号>`，避免覆盖原图。

参数冲突、路径不存在、阈值顺序错误时立即终止，并输出明确的中文错误信息。

## 5. 数据流

### 5.1 YOLO 检测

两张图片通过同一个 YOLO 实例进行推理。每个检测结果保留：

- 类别 ID 和类别名称；
- 检测置信度；
- 原图坐标系中的 `xyxy` 检测框；
- 原图尺寸。

同一类别出现多个框时，第一版只保留置信度最高的框。该规则适用于当前以单车主体和单个主要部件为主的实验场景，并在 JSON 中记录选择后的检测框，避免隐式匹配。

### 5.2 部件配对

仅当同一类别在备案图和实拍图中都达到检测阈值时，才进入 Level 2 外观比对。

- 双方均检测到：进入 DINOv2 特征比对。
- 仅一方检测到：记录为 `unmatched`，不计算相似度。
- 双方均未检测到：不输出该类别。

Demo 不把单图漏检直接解释为拆除或加装，因为遮挡、视角和检测置信度都可能造成漏检。

### 5.3 部件裁剪

检测框先取整并限制在图像边界内，然后从原图裁剪。空框、宽高为零或无法读取的裁剪会被明确记录为失败，不进入特征提取。

第一版采用检测框紧裁剪，不额外扩边。这样可以保持算法与技术方案一致，也能建立明确基线。后续如需验证背景上下文对结果的影响，再增加独立实验参数，而不是改变默认行为。

### 5.4 DINOv2 特征

使用 Meta FAIR 官方 DINOv2 ViT-B/14 预训练权重：

1. 将 RGB 部件图按 DINOv2 官方预处理转换为 `224 x 224` 输入。
2. 提取归一化后的 CLS token，特征维度为 768。
3. 再执行一次显式 L2 归一化，确保余弦相似度计算稳定。
4. 在同一批次内提取备案图和实拍图的部件特征，减少重复推理。

首次运行需要下载 DINOv2 权重。下载失败时输出模型来源和缓存说明，不用空特征或随机特征继续执行。

### 5.5 相似度分档

使用余弦相似度，并按技术方案初始阈值输出：

| 相似度                | 结果代码       | 中文判定             |
| --------------------- | -------------- | -------------------- |
| `>= 0.80`             | `consistent`   | 部件一致             |
| `>= 0.60` 且 `< 0.80` | `review`       | 疑似更换，需人工复核 |
| `< 0.60`              | `inconsistent` | 部件外观不一致       |

阈值边界采用左闭区间，保证 `0.80` 和 `0.60` 的行为确定。阈值可配置，但输出中必须记录本次实际使用值。

## 6. 输出设计

每次运行创建独立结果目录，包含：

- `comparison.json`：机器可读的完整结果。
- `comparison_summary.jpg`：备案图和实拍图的检测框、公共部件相似度及分档汇总。
- `crops/<part>/reference.jpg`：备案图部件裁剪。
- `crops/<part>/actual.jpg`：实拍图部件裁剪。
- `crops/<part>/comparison.jpg`：该部件左右对照图，标注检测置信度、相似度和判定。

`comparison.json` 至少包含：

```json
{
    "reference_image": ".../reference_3c.jpg",
    "actual_image": ".../actual_left_front_45.jpg",
    "detector": ".../yolo11l_12000_best.pt",
    "feature_model": "dinov2_vitb14",
    "thresholds": {
        "detection": 0.6,
        "consistent": 0.8,
        "review": 0.6
    },
    "matched_parts": [
        {
            "part": "saddle",
            "reference_confidence": 0.93,
            "actual_confidence": 0.79,
            "similarity": 0.72,
            "verdict": "review"
        }
    ],
    "unmatched_parts": []
}
```

示例中的 `similarity` 是格式示例值，不是预设实验结果；实际值必须由模型推理生成。

控制台同步输出中文表格，便于不打开文件时快速查看部件、双方置信度、相似度和判定。

## 7. 代码边界

Demo 放在 `validate/part_feature_compare/` 独立实验目录，不修改 Ultralytics 核心包。实现优先复用：

- `ultralytics.YOLO` 和 `Results.boxes`；
- PyTorch 张量归一化和余弦相似度；
- Pillow/OpenCV 的图像读取、裁剪和可视化能力；
- DINOv2 官方预训练模型接口。

第一版不增加 FAISS、FastAPI、数据库、批量订单调度、Level 3 结构比对或阈值自动标定。这些能力都不属于单对图片技术验证的必要范围。

## 8. 异常处理

- 输入图片或权重不存在：启动前失败。
- 图片损坏或无法解码：指出具体图片路径后失败。
- 某张图无检测结果：生成包含原因的 JSON，并以非零退出码结束。
- 没有共同部件：生成检测和未匹配清单，不加载 DINOv2，明确提示无法执行 Level 2。
- DINOv2 权重下载或加载失败：指出网络或缓存问题，不产生伪造结果。
- 单个检测框裁剪无效：跳过该部件并记录错误，其他有效部件继续比较。
- 输出目录已存在：创建可预测的运行子目录，禁止覆盖输入图片。

## 9. 测试与验收

单元测试覆盖：

- `0.80`、`0.60` 两个相似度边界；
- 同类别多框选择最高置信度；
- 检测框越界限制和空框拒绝；
- 共同部件与单侧部件分类；
- L2 归一化后的相似度计算；
- JSON 字段和阈值记录。

真实样例验收覆盖：

1. 指定 YOLO 权重可加载。
2. 默认订单两张图片可读取。
3. 至少对共同检测到的部件生成实际 DINOv2 相似度。
4. JSON、汇总图和部件裁剪图全部生成。
5. JSON 中的框、置信度、相似度与可视化文字一致。
6. 运行说明中的命令可从仓库环境直接执行。

## 10. 当前结论边界

本 Demo 的成功标准是证明“检测、同类部件配对、特征提取、余弦相似度、分档和证据输出”完整可运行，不是证明 `0.80` 和 `0.60` 已适用于生产。

生产阈值必须使用同视角的真实正样本对和改装负样本对标定。当前样例视角不完全一致，任何低分都需要先排除视角、尺度、遮挡和裁剪范围影响，再讨论部件是否发生变化。
