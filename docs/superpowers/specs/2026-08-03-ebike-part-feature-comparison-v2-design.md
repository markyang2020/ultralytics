# 电动自行车部件特征比对 Demo V2 设计

## 1. 目标

在现有 YOLO 部件检测和 DINOv2 RGB CLS 相似度基线之上，增加一条可独立核对的实验特征通道，验证灰度域归一化、前景加权局部特征和形状特征是否能降低已确认合格车辆的误拒。

V2 是单对图片技术实验，不把经验权重或现有阈值解释为生产准确率。原始 RGB CLS 分数继续输出，确保每次实验都能回答“新方法相对同一输入的基线发生了什么变化”。

## 2. 设计约束

- 不修改 `ultralytics/` 核心包，继续复用现有 YOLO 检测、同类部件配对、结果落盘和可视化实现。
- 不复制现有脚本形成第二条完整流水线，V1 和 V2 共用检测框、裁剪图和输出目录。
- 不依赖当前官方 DINOv2 Hub 模型未提供的 `get_last_selfattention()` 接口。
- 不引入 `scikit-image`；形状特征使用项目已有的 OpenCV 和 NumPy 实现。
- 不把形状余弦相似度从 `[0, 1]` 再映射到 `[0.5, 1]`，避免实验分数被人为抬高。
- 不用低分直接证明部件改装；基线和实验分档都保留“实验阈值、未完成生产标定”的边界。
- 双方部件使用相同预处理流程，禁止只对实拍图去背景而制造新的处理差异。

## 3. 方案选择

### 3.1 原样接入附件实现

优点是代码改动直观。缺点是注意力 API 与当前官方模型不兼容，需要新增 `scikit-image`，非负形状相似度的二次映射会系统性抬高结果，且只对实拍图执行 GrabCut 会引入不对称处理。因此不采用。

### 3.2 修正后集成现有流水线

保留原 RGB CLS 基线，新增相同输入上的灰度局部语义和形状通道，共用报告与证据输出。该方案能做逐部件消融对照，不重复 YOLO 和编排逻辑，也不会把实验分数伪装成旧字段的自然提升，因此采用。

### 3.3 单独创建 V2 脚本

可以完全隔离实验，但会复制输入解析、检测、配对、异常处理、JSON 和可视化代码，后续修复容易在两条流水线间漂移，因此不采用。

## 4. 数据结构

每个已配对部件保留原始裁剪图，并新增以下信息：

- `baseline`：原始 RGB 裁剪的 DINOv2 CLS 余弦相似度和原有分档。
- `experimental.gray_dino_similarity`：灰度归一化输入的 CLS 与前景加权 patch token 融合特征相似度。
- `experimental.shape_similarity`：HOG 与边缘空间分布组成的形状特征相似度。
- `experimental.fused_similarity`：按部件实验权重融合后的分数。
- `experimental.channel_gap`：语义通道与形状通道的分数差，用于暴露通道冲突，不把它伪装成概率置信度。
- `experimental.weights`：本次实际使用的部件权重，保证实验可复现。
- `experimental.verdict`：使用当前实验阈值得到的独立分档，不覆盖基线分档。

顶层报告分别提供 `baseline_verdict` 和 `experimental_verdict`。为保持现有 JSON 消费者可用，原有 `verdict` 和 `similarity` 字段继续表示基线结果；新增字段均带 `experimental` 语义。

## 5. 统一预处理

双方部件裁剪执行相同过程：

1. 将 RGB 裁剪转为灰度图。
2. 对裁剪增加白色边界，再以检测框中心为先验生成前景掩码。
3. 对掩码结果做有效性检查；掩码为空或只覆盖极小区域时，明确记录前景提取失败并使用完整裁剪作为实验输入。
4. 用白色填充背景，对前景灰度执行 CLAHE 和轻量高斯去噪。
5. 按原始长宽比缩放到 `256 x 256` 白底画布，不直接拉伸形状。
6. 同步生成归一化前景掩码和 Canny 边缘图。

预处理产物保存到每个部件的证据目录，包括双方灰度图、掩码和边缘图。任何 fallback 都写入 JSON，避免实验人员只看到分数而不知道前景提取是否生效。

## 6. 特征提取

### 6.1 基线通道

继续对原始 RGB 裁剪执行现有 DINOv2 ViT-B/14 官方预处理，读取 `x_norm_clstoken`，得到 768 维 L2 归一化特征。该路径的数值应与 V1 保持一致。

### 6.2 灰度局部语义通道

将归一化灰度图复制为三通道后输入同一个 DINOv2 ViT-B/14 实例，读取：

- `x_norm_clstoken`；
- `x_norm_patchtokens`，在 `224 x 224`、patch size 14 下应为 256 个 768 维 token。

前景掩码缩放为 `16 x 16` patch 权重。对 patch token 做前景加权平均，再与灰度 CLS 按实验系数融合并执行 L2 归一化。该实现直接使用官方 `forward_features()` 返回值，不访问不存在的注意力 API。

### 6.3 形状通道

在归一化灰度前景图上提取：

- OpenCV HOG 方向梯度特征；
- Canny 边缘图的 `16 x 16` 空间分布。

两类特征拼接后执行 L2 归一化。该通道描述当前二维投影下的形状，不宣称具备跨任意视角的不变性。

## 7. 相似度与融合

各通道分别计算归一化向量的余弦相似度：

```text
baseline_similarity = cosine(rgb_cls_ref, rgb_cls_actual)
gray_dino_similarity = cosine(gray_dino_ref, gray_dino_actual)
shape_similarity = cosine(shape_ref, shape_actual)
fused_similarity = dino_weight * gray_dino_similarity
                 + shape_weight * shape_similarity
```

部件权重沿用附件给出的实验初值，但必须在 JSON 和 README 中标为未标定参数。未知类别使用等权重。融合只发生在灰度 DINO 和形状通道之间，原始 RGB CLS 不参与融合，以便基线保持独立。

基线和实验分数分别使用当前命令行阈值分档。控制台、JSON 和图片同时展示两组结果；程序不得因为实验分数较高就声称准确率提升。

## 8. 流水线与输出

完整数据流为：

```text
两张原图
  -> 同一个 YOLO 实例检测
  -> 同类部件配对
  -> 共用原始裁剪
  -> RGB CLS 基线
  -> 统一灰度/前景/边缘预处理
  -> 灰度局部 DINO + 形状特征
  -> 独立分数和分档
  -> JSON、控制台、汇总图和逐部件证据图
```

每个部件目录在原有三张图片之外新增：

```text
reference_preprocessed.jpg
actual_preprocessed.jpg
reference_mask.png
actual_mask.png
reference_edges.png
actual_edges.png
```

逐部件对照图显示基线 CLS、灰度 DINO、形状和融合分数。汇总图保留检测置信度，并优先显示基线与实验融合分数，避免标签过长遮挡车辆。

## 9. 异常处理

- 图片无法解码、YOLO 权重不存在、阈值顺序错误：沿用现有明确失败行为。
- DINOv2 未返回 CLS 或 patch token、特征维度不是 768、patch 数量无法还原为空间网格：中止实验并指出具体字段或维度。
- 前景提取失败：记录 fallback 原因，使用完整灰度裁剪继续生成实验特征。
- HOG 或边缘特征范数为零：返回零向量并把该通道标为不可用；融合时不把不可用通道的固定零分数解释为部件不一致。
- 没有共同部件：仍不加载特征模型，维持现有行为。

## 10. 测试设计

单元测试按 TDD 新增以下行为：

1. 双方相同输入经过统一预处理后得到相同灰度图和掩码。
2. 非正方形部件缩放后保持长宽比，未被拉伸填满画布。
3. 官方 DINOv2 返回的 CLS 和 patch token 能生成归一化灰度局部特征，不调用注意力 API。
4. 前景权重只聚合掩码覆盖的 patch；空掩码触发明确 fallback。
5. HOG 与边缘特征输出维度稳定并完成 L2 归一化。
6. 形状相似度不执行 `(cos + 1) / 2`，避免分数虚高。
7. 部件权重正确参与融合，通道不可用时只使用有效通道重新归一化权重。
8. JSON 同时保留基线和实验结果、权重、通道可用性与 fallback 信息。
9. 可视化证据文件全部生成，旧的原始裁剪和汇总图仍保留。
10. V1 测试继续通过，证明检测、配对、输入解析和基线行为未回归。

真实验证使用现有已核验合格订单，比较每个部件的 V1 和 V2 分数，并人工检查掩码、灰度图和边缘图。该验证只能说明实验方向和失败模式，生产收益必须在包含真实改装负样本的独立数据集上评估。

## 11. 完成标准

- 现有基线分数在相同模型、输入和设备下保持一致。
- 每个共同部件均输出完整实验分项、融合权重和预处理证据。
- 附件中的三条核心思路均有对应实现，但不包含不兼容 API、缺失依赖或分数虚高映射。
- 单元测试、Ruff、语法检查和 CLI 帮助检查通过。
- 至少一组真实订单完成 YOLO + 官方 DINOv2 V2 推理，JSON 数值和可视化内容一致。
- README 明确运行方法、输出字段、实验边界及生产标定要求。
